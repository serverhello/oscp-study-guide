Learning Units:

**Enumeration** = identifying, categorizing, and listing components/resources within the target. Process is **recursive** — a discovery (vuln, credential, resource) can grant further access, which restarts enumeration from a new vantage point.

Two perspectives covered in this module:
- **External/unauthenticated** — attacker on the internet, no CSP API credentials yet.
- **Internal/authenticated** — attacker already has compromised IAM credentials, uses the CSP's API directly.

## 25.2 Reconnaissance of Cloud Resources on the Internet

Objectives: Perform Domain and Subdomain Reconnaissance; Identify Service-specific Domains.

Per NIST's Cloud Computing definition, cloud resources have an inherent aspect of **public accessibility** ("ubiquitous", "convenient", "broad network access"). Some resources are *meant* to be public (OS images); others are internal components (network interfaces, virtual disks) that may be unintentionally exposed via misconfiguration. Attacker's goal: find both intentionally and unintentionally public resources — **without needing authenticated access to the CSP API**.

### 25.2.1 Accessing the Lab

After deployment you receive: **Public DNS IP Address**, **domain name of the target**, and **credentials for the IAM user `attacker`** (`ACCESS_KEY_ID` / `SECRET_ACCESS_KEY`).

Configure local DNS to point at the lab's custom DNS server so name resolution works against the lab domain:

```bash
cat /etc/resolv.conf
# Generated by NetworkManager
nameserver 1.1.1.1

sudo nano /etc/resolv.conf
# Add a new nameserver line at the TOP of the file:
nameserver 44.205.254.229          # lab's public DNS IP (changes every restart)

# Verify with host tool against the new lab nameserver and the system default
host www.offseclab.io 44.205.254.229
host www.offseclab.io
```

> **Tip** — The public IP address of the lab DNS server changes every time you restart the lab; you must reconfigure `resolv.conf` again each restart.

> **Tip** — Some ISPs block queries to external/arbitrary DNS servers. If both `host` commands fail, tether via a mobile hotspot as a workaround. Worst case, this only affects the Domain Reconnaissance section.

Reset DNS when done (NetworkManager overwrites `resolv.conf` on network/service restart anyway):

```bash
sudo systemctl restart NetworkManager
cat /etc/resolv.conf     # back to nameserver 1.1.1.1
```

### 25.2.2 Domain and Subdomain Reconnaissance

Starting point: only the domain name, e.g. `offseclab.io`.

```bash
# Query the nameservers (NS records) for the domain
host -t ns offseclab.io
# offseclab.io name server ns-1536.awsdns-00.co.uk.
# offseclab.io name server ns-512.awsdns-00.net.
# offseclab.io name server ns-0.awsdns-00.com.
# offseclab.io name server ns-1024.awsdns-00.org.

# The "awsdns" naming pattern strongly suggests Route53. Confirm via whois:
whois awsdns-00.com | grep "Registrant Organization"
# Registrant Organization: Amazon Technologies, Inc.

# Get the public IP of the main site
host www.offseclab.io
# www.offseclab.io has address 52.70.117.69

# Reverse DNS + whois on that IP
host 52.70.117.69
# 69.117.70.52.in-addr.arpa domain name pointer ec2-52-70-117-69.compute-1.amazonaws.com

whois 52.70.117.69 | grep "OrgName"
# OrgName:  Amazon Technologies Inc.
```

The reverse-lookup PTR (`ec2-...compute-1.amazonaws.com`) confirms the resource is hosted on **AWS EC2**.

> **Tip** — EC2 is a common AWS service for virtual machines, applications, and other services requiring a server.

> The domain being hosted on AWS doesn't guarantee the *rest* of the infrastructure is on AWS — keep digging and treat this whole process as recursive (repeat for every new domain/subdomain/IP found).

Automate subdomain discovery / zone transfer attempts with `dnsenum`:

```bash
dnsenum offseclab.io --threads 500
```
`dnsenum` re-confirms name servers + public IP, attempts **zone transfers (AXFR)** against each nameserver, and brute-forces subdomains using its bundled dictionary (`/usr/share/dnsenum/dns.txt`).

**Takeaways from this stage:**
- Domain service hosted in AWS → likely Route53.
- Domain resolves to a public IP also owned by AWS → EC2.
- That public IP serves multiple sites (all running inside the same EC2 instance).

### 25.2.3 Service-specific Domains

Public CSPs use predictable custom domain suffixes to address their services — you already saw this with `compute-1.amazonaws.com` (EC2 PTR naming). Leverage these naming conventions to enumerate cloud resources tied to the target.

**Manual discovery via browser** — inspect page source / Developer Tools (F12) → Network tab, reload the page, look at loaded resources (images, CSS, JS). An image request pointing at `s3.amazonaws.com` reveals an **S3 bucket**.

From a URL like:
```
http://s3.amazonaws.com/offseclab-assets-public-axevtewi/sites/www/images/saphire.jpg
```
- Bucket name: `offseclab-assets-public-axevtewi`
- Object key: `sites/www/images/saphire.jpg`

> **Tip** — If local DNS to the public server is broken, get the bucket name via AWS CLI `s3 ls` with the attacker profile instead.

> **Tip** — AWS internally redirects `s3.amazonaws.com` to a region-specific endpoint, e.g. `s3.us-east-1.amazonaws.com`. This region-in-URL behavior may not hold for other AWS services.

**Test if the bucket itself is listable** — browse `http://<bucket_name>.s3.amazonaws.com/` (strip the object key). Expected: `AccessDenied`. If instead you get an XML listing of every object — the bucket allows public listing, a misconfiguration.

> **Tip** — Objects can be public inside a bucket *without* the bucket itself having public access enabled (and vice versa) — these are two separate settings.

**Bucket naming convention pattern observed:** `<org>-<description>-<random-string>` (e.g. `offseclab-assets-public-axevtewi`). Random suffix exists because bucket names must be globally unique per region, and also hinders naive enumeration.

> **Tip** — If a bucket exists but isn't public, you'll typically see a different error (still confirms existence, distinguishable from a nonexistent bucket) — useful as an existence oracle when guessing bucket-name variants (`-dev`, `-private`, etc.).

Custom cloud-provider URL suffixes to search for (multi-cloud OSINT):

| AWS | Azure | GCP |
|---|---|---|
| `s3.amazonaws.com` | `web.core.windows.net` | `appspot.com` |
| `awsapps.com` | `file.core.windows.net` | `storage.googleapis.com` |
| | `blob.core.windows.net` | |
| | `azurewebsites.net` | |
| | `cloudapp.net` | |

**`cloud-enum`** — multi-cloud bucket/resource enumeration tool (installed as package `cloud-enum`, but the binary is `cloud_enum`):

```bash
sudo apt update
sudo apt install cloud-enum
```

> **Warning** — Package name is `cloud-enum`; the actual command is `cloud_enum` (underscore).

```bash
cloud_enum --help
```

Key `cloud_enum` options:

| Flag | Purpose |
|---|---|
| `-k KEYWORD`, `--keyword` | keyword to search (repeatable) |
| `-kf KEYFILE`, `--keyfile` | file with one keyword per line |
| `-m MUTATIONS`, `--mutations` | extra word list for mutation-based guessing (default `/usr/lib/cloud-enum/enum_tools/fuzz.txt`) |
| `-b BRUTE`, `--brute` | list to brute-force Azure container names (same default file) |
| `-t THREADS`, `--threads` | HTTP brute-force threads (default 5) |
| `-ns NAMESERVER`, `--nameserver` | DNS server to use for brute-force |
| `-l LOGFILE`, `--logfile` | append found items to file |
| `-f FORMAT`, `--format` | log format: text/json/csv |
| `--disable-aws` / `--disable-azure` / `--disable-gcp` | skip a CSP |
| `-qs`, `--quickscan` | disable mutations + second-level scans |

```bash
# Quick scan against a known bucket name, AWS-only
cloud_enum -k offseclab-assets-public-axevtewi --quickscan --disable-azure --disable-gcp

# Build a custom keyfile of likely bucket-name variants
echo -n "offseclab-assets-public-axevtewi
offseclab-assets-private-axevtewi
offseclab-assets-dev-axevtewi
offseclab-assets-prod-axevtewi
offseclab-assets-development-axevtewi
offseclab-assets-production-axevtewi" | tee /tmp/keyfile.txt

# Run cloud_enum against the keyfile
cloud_enum -kf /tmp/keyfile.txt -qs --disable-azure --disable-gcp
```
Output flags each bucket as **OPEN** (public, lists files), **Protected** (exists, not publicly listable), or absent (doesn't exist).

**Getting the bucket name with curl instead of a browser** (25.3.3 reuses this):

```bash
curl -s www.offseclab.io | grep -o -P 'offseclab-assets-public-\w{8}'
```
`-s` suppresses curl's progress meter; `-P` tells grep to use Perl-compatible regex; `-o` prints only the matched substring.

**Takeaways:**
- Discovering publicly-accessible cloud resources isn't inherently a security problem, but misconfigurations grant excessive permissions.
- An org using one CSP doesn't preclude simultaneous use of others — cloud deployment is flexible/multi-cloud.

## 25.3 Reconnaissance via Cloud Service Provider's API

Objectives: Obtain Information from Publicly Shared Resources; Obtain Account IDs from Public S3 Buckets; Enumerate IAM Users in Other Accounts.

CSPs generally expose two access paths: a **web console** (username/password/MFA) and a programmatic **API** (public, but requires authentication). This section abuses the API from an (simulated) external attacker account.

**IAM (Identity and Access Management)** = the AWS service that manages users and their permissions.

### 25.3.1 Preparing

Install AWS CLI:

```bash
sudo apt update
sudo apt install -y awscli
```

Configure a **named profile** (best practice — lets you quickly switch between IAM identities):

```bash
aws configure --profile attacker
# AWS Access Key ID []: AKIAQO...
# AWS Secret Access Key []: cOGzm...
# Default region name []: us-east-1
# Default output format []: json

# Validate the credentials work
aws --profile attacker sts get-caller-identity
```
Successful JSON response (UserId/Account/Arn) proves the credentials are valid and you're interacting with the AWS API as that identity. Every subsequent command needs `--profile attacker` (or whichever profile).

### 25.3.2 Obtaining Information from Publicly Shared Resources

Some cloud assets are meant to be public (standard OS images for EC2). Others are internal but sometimes get **shared across accounts or publicly** by large orgs (custom AMIs, snapshots, DB snapshots).

> **Warning** — Ideally shared resources contain no sensitive data (shared-responsibility model), but this isn't always true in practice.

Focus resources for this section: publicly shared **AMIs**, **EBS snapshots**, **RDS snapshots**.

> **Warning** — Unless stated otherwise, every command below uses the `attacker` profile.

**AMIs (Amazon Machine Images)** — pre-built VM images (OS + software) required to launch an EC2 instance.

```bash
# List all AMIs owned by Amazon (may take 30-60s)
aws --profile attacker ec2 describe-images --owners amazon
```
`--owners <AccountID>` lists AMIs owned by a specific account. `--executable-users all` includes AMIs shared with (executable by) any account, not just fully public ones.

**Filtering AMIs by keyword** — filter syntax:

```bash
--filters "Name=<filter-name>,Values=<filter-value1,filter-value2,...>"
```

```bash
# Filter by description containing "offseclab" (no match in this example)
aws --profile attacker ec2 describe-images --executable-users all \
  --filters "Name=description,Values=*offseclab*"

# Filter by name instead — this one hits
aws --profile attacker ec2 describe-images --executable-users all \
  --filters "Name=name,Values=*Offseclab*"
```
A match reveals the AMI's `OwnerId` — very likely the **target's AWS Account ID**. That Account ID can now be used to pivot into further searches (`--owners <AccountID>` against other resource types).

**EBS snapshots:**

```bash
aws --profile attacker ec2 describe-snapshots --filters "Name=description,Values=*offseclab*"
```

There's no universal recipe — technique depends on the resource type, service API, and CSP; consult the specific service's API documentation for filterable attributes. Finding these public resources (even without direct sensitive data) widens the attack surface — e.g. you can launch an EC2 instance from a discovered AMI and dig through it for secrets/config left behind.

### 25.3.3 Obtaining Account IDs from S3 Buckets

Goal: derive the target's AWS **Account ID** purely by abusing IAM policy **Conditions** against a *publicly readable* S3 bucket/object — without any publicly shared resource metadata.

Technique overview:
1. Identify a publicly-readable bucket/object owned by the target (readable by *any* IAM identity in *any* account).
2. Create a new IAM user in the attacker's own account (new users have **zero permissions by default** — deny-all).
3. Attach an inline policy to that user granting `s3:ListBucket` / `s3:GetObject`, but scoped with a `Condition` requiring the resource's owning account ID to match a partial digit pattern (`s3:ResourceAccount`).
4. Test: if access succeeds, the digit guess was correct for that position; iterate 0-9 per digit until the entire account ID is recovered.

```bash
# Re-derive the current bucket name (random suffix changes on lab restart)
curl -s www.offseclab.io | grep -o -P 'offseclab-assets-public-\w{8}'
```

```bash
# Create the attacker-side test IAM user + access keys
aws --profile attacker iam create-user --user-name enum
aws --profile attacker iam create-access-key --user-name enum
# Note AccessKeyId + SecretAccessKey from output

aws configure --profile enum
aws sts get-caller-identity --profile enum
```

> New IAM users are implicitly deny-all until a policy is attached — even for actions against a bucket that's technically public.

> **Note (lab-only caveat)**: in the real world the `enum` user lives in the *attacker's* account, separate from the target. In this lab both the `enum` user and target bucket share the same AWS account, so IAM allows the user to read public buckets *in that same account* by default. The lab therefore has you test against the **private** bucket instead of the public one, to accurately simulate cross-account behavior.

Policy JSON — grant list/read only if the bucket's owning account ID starts with a given digit:

```json
# policy-s3-read.json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowResourceAccount",
            "Effect": "Allow",
            "Action": [
                "s3:ListBucket",
                "s3:GetObject"
            ],
            "Resource": "*",
            "Condition": {
                "StringLike": {"s3:ResourceAccount": ["0*"]}
            }
        }
    ]
}
```

```bash
aws --profile attacker iam put-user-policy \
  --user-name enum \
  --policy-name s3-read \
  --policy-document file://policy-s3-read.json

# Verify it attached
aws --profile attacker iam list-user-policies --user-name enum
```

> **Warning** — Policies take ~10-15 seconds to become active after being applied; wait before re-testing.

```bash
# Test — fails, account doesn't start with "0"
aws --profile enum s3 ls offseclab-assets-private-kaykoour
# AccessDenied

# Edit the Condition to "1*", re-apply, retest — succeeds
aws --profile attacker iam put-user-policy --user-name enum --policy-name s3-read \
  --policy-document file://policy-s3-read.json
aws --profile enum s3 ls offseclab-assets-private-kaykoour
# PRE sites/
```

Continue narrowing digit-by-digit:

```
"StringLike": {"s3:ResourceAccount": ["10*"]}
"StringLike": {"s3:ResourceAccount": ["11*"]}
...
"StringLike": {"s3:ResourceAccount": ["19*"]}
```

> This can be scripted end-to-end. The tool **`s3-account-search`** implements the same idea but uses **roles** instead of users as the vehicle for the Condition-based probe.

> The core generalizable concept: abuse the `Condition` element of IAM policies to leak information (here, account ID) through side-channel Allow/Deny behavior. S3 is used here because public S3 objects are common, but the technique conceptually extends to other services.

### 25.3.4 Enumerating IAM Users in Other Accounts

Cross-account access in AWS requires specifying a `Principal` (the account + IAM identity — User, Group, or Role) that is allowed to access a resource. **AWS validates the Principal exists** when you try to apply the policy — a nonexistent principal causes an error. This becomes an **existence oracle** for usernames/role names in a target account, even without ever touching a resource in that account.

ARN format for an IAM Principal:

```json
"Principal": {
    "AWS": ["arn:aws:iam::AccountID:user/user-name"]
}
```

Example — testing whether `cloudadmin` exists in account `123456789012`:

```json
"Principal": {
    "AWS": ["arn:aws:iam::123456789012:user/cloudadmin"]
}
```

**S3 bucket-policy based user enumeration:**

```bash
# 1. Create a throwaway bucket in the attacker's own account
aws --profile attacker s3 mb s3://offseclab-dummy-bucket-$RANDOM-$RANDOM-$RANDOM
# make_bucket: offseclab-dummy-bucket-28967-25641-13328
```

```json
# grant-s3-bucket-read.json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowUserToListBucket",
            "Effect": "Allow",
            "Resource": "arn:aws:s3:::offseclab-dummy-bucket-28967-25641-13328",
            "Principal": {
                "AWS": ["arn:aws:iam::123456789012:user/cloudadmin"]
            },
            "Action": "s3:ListBucket"
        }
    ]
}
```

```bash
# Attach the resource-based policy to the bucket
aws --profile attacker s3api put-bucket-policy \
  --bucket offseclab-dummy-bucket-28967-25641-13328 \
  --policy file://grant-s3-bucket-read.json
# No error returned => the user "cloudadmin" DOES exist in account 123456789012
```

```bash
# Test a name you suspect does NOT exist
cp grant-s3-bucket-read.json grant-s3-bucket-read-userDoNotExist.json
nano grant-s3-bucket-read-userDoNotExist.json    # change principal to .../user/nonexistant

aws --profile attacker s3api put-bucket-policy \
  --bucket offseclab-dummy-bucket-28967-25641-13328 \
  --policy file://grant-s3-bucket-read-userDoNotExist.json
# An error occurred (MalformedPolicy) when calling the PutBucketPolicy operation:
# Invalid principal in policy
```

> The `Invalid principal in policy` error is misleading — it's not a syntax problem, it's that AWS **couldn't validate the principal exists**. This is the enumeration oracle: error = doesn't exist, success = exists.

> This works for any Principal type — Users, Groups, or **Roles**.

**Role enumeration via `AssumeRole` trust policy** — same principle: when creating a role you set a *trust policy* naming which principals may assume it. An invalid/nonexistent principal in that trust policy errors out the same way.

```bash
# Build a wordlist of candidate role names
echo -n "lab_admin
security_auditor
content_creator
student_access
lab_builder
instructor
network_config
monitoring_logging
backup_restore
content_editor" > /tmp/role-names.txt
```

**Pacu** — automates this User/Role enumeration technique.

```bash
sudo apt install pacu
pacu -h
```

`pacu` CLI flags:

| Flag | Purpose |
|---|---|
| `--session <name>` | select a session |
| `--new-session <name>` | create a new session |
| `--activate-session` | activate a session |
| `--set-keys` | alias, access id, secret key, token |
| `--module-name <name>` | select module |
| `--data <service/all>` | show collected data |
| `--module-args '...'` | pass args to module |
| `--list-modules` | list modules |
| `--pacu-help` | show Pacu's help window |
| `--module-info` | info on a module (needs `--module-name`) |
| `--exec` | execute the module |
| `--set-regions [...]` | set target regions, or `all` |
| `--whoami` | show current IAM identity |

```bash
pacu
# What would you like to name this new session? offseclab

# Import credentials already configured in AWS CLI profile "attacker"
Pacu (offseclab:No Keys Set) > import_keys attacker
Pacu (offseclab:imported-attacker) >

# List all modules
Pacu (offseclab:imported-attacker) > ls
# [Category: RECON_UNAUTH]
# iam__enum_roles
# iam__enum_users

# Help for a module
Pacu (offseclab:imported-attacker) > help iam__enum_roles
```

`iam__enum_roles` usage: `pacu [--word-list WORD_LIST] [--role-name ROLE_NAME] --account-id ACCOUNT_ID`. It probes for existing roles by trying to update the target role's `AssumeRole` policy document (using either a role you specify via `--role-name`, or a temp role it creates itself). For safety it always sets an **explicit deny** against your own account/role during the update, so no real trust relationship is ever opened. Best run with **personal AWS access keys** — it spams CloudTrail with `iam:UpdateAssumeRolePolicy` and a few `sts:AssumeRole` log entries; the *target* account sees nothing unless the role is actually assumable (and even then, only if the target is monitoring `AssumeRole` events tied to your identity).

```bash
Pacu (offseclab:imported-attacker) > run iam__enum_roles --word-list /tmp/role-names.txt --account-id 123456789012
# [iam__enum_roles] Found role: arn:aws:iam::123456789012:role/lab_admin
# [iam__enum_roles] Role can be assumed, but hit max session time limit, reverting to minimum of 1 hour...
# [iam__enum_roles] Successfully assumed role for 1 hour: arn:aws:iam::123456789012:role/lab_admin
# { "Credentials": { "AccessKeyId": ..., "SecretAccessKey": ..., "SessionToken": ..., "Expiration": ... } }
```
Not only does the module discover existing role names — if the discovered role's trust policy happens to allow your account, it **automatically assumes it** and hands you temporary credentials.

> All of this interaction happens through the *attacker's own account*, so related CloudTrail events are logged there — leaving **no trace in the target's account**.

## 25.4 Initial IAM Reconnaissance

Objectives: Examining Compromised Credentials; Scoping IAM Permissions.

Scenario shift: attacker has already achieved **initial compromise** and holds valid credentials to the target's cloud environment. Now the goal is footprinting: which accounts/keys are compromised, and what's their level of access?

> Public clouds log user activity by default, but monitoring/alerting maturity varies. Skilled attackers keep actions within the compromised credential's *authorized* scope to minimize detection during early enumeration.

### 25.4.1 Accessing the Lab

Lab provides (via console info box):
- Target user credentials: **Access Key ID** / **Secret Access Key**
- Challenge user credentials (Access Key ID / Secret Access Key) — simulates an *external* AWS account for stealthier techniques
- Monitoring user: **Management Console login URL**, **Username**, **Password** — used to inspect CloudTrail as a "defender" would

### 25.4.2 Examining Compromised Credentials

```bash
aws configure --profile target
# AWS Access Key ID []: AKIAVXWRNA7HUYFERLHS...
# AWS Secret Access Key []: u1CmqAO9QR...
# Default region name []: us-east-1
# Default output format []: json
```

**Step 1 — validate the account / identify who you are:**

```bash
aws --profile target sts get-caller-identity
# {
#   "UserId": "AIDAQOMAIGYUYNMOIF46I",
#   "Account": "123456789012",
#   "Arn": "arn:aws:iam::123456789012:user/support/clouddesk-plove"
# }
```
Reveals: **UserId** (unique IAM user identifier), **Account** (AWS account ID), **Arn** (full identity — here IAM username `clouddesk-plove`, IAM **path** `/support/`).

> **Tip** — IAM Paths are optional identifiers used to group related identities to mirror the org's structure.

> **Tip** — `sts:GetCallerIdentity` **never returns AccessDenied**, even if an admin explicitly denies it in a policy — because the same identity info is embedded in the AccessDenied response anyway. No permissions are required for this call.

> This call **is logged** in CloudTrail's Event History — a common attacker "first move" that blue teams should specifically alert on.

**Stealthier alternative #1 — `iam get-access-key-info`:** run this from an *external* (attacker-controlled) account/profile so the CloudTrail log entry lands in the attacker's own account, not the target's.

```bash
aws configure --profile challenge
aws --profile challenge iam get-access-key-info --access-key-id AKIAQOMAIGYUVEHJ7WXM
# { "Account": "123456789012" }
```
This determines the account ID tied to an access key ID, without generating a log event that the target would see.

**Stealthier alternative #2 — abuse an unlogged error response.** CloudTrail's **data events** and **insights events** are not shown in default Event History. Invoking a Lambda function is a data event, so triggering an error on a *nonexistent* Lambda leaks the same identity info via the error message, without appearing in the default event history:

```bash
aws --profile target lambda invoke \
  --function-name arn:aws:lambda:us-east-1:123456789012:function:nonexistent-function outfile
# An error occurred (AccessDeniedException) when calling the Invoke operation: User:
# arn:aws:iam::123456789012:user/support/clouddesk-plove is not authorized to perform:
# lambda:InvokeFunction on resource: ... because no resource-based policy allows the
# lambda:InvokeFunction action
```

> There's no definitive list of which actions are unlogged by default — consult CloudTrail's docs on data/insight events. These *can* still be captured if a Trail is explicitly configured to log them.

**Region evasion consideration:** CloudTrail Event History (by default) is scoped per-region in the console view. Running the same command in an unusual region can reduce the chance a defender notices it:

```bash
aws --profile target sts get-caller-identity --region us-east-2
```
A defender monitoring only `us-east-1`'s Event History misses a `GetCallerIdentity` call made against `us-east-2`.

> **Warning / defender takeaway** — mitigate this by restricting which regions the account may operate in and by monitoring **all** enabled regions, not just the default one.

**Scoping IAM permissions** — IAM = the umbrella term for AWS's identity/access resources (Users, Groups, Roles, Policies). **Principle of Least Privilege (PoLP)** = best practice: grant only the minimum permissions needed. Overly-permissive identities remain a leading root cause of cloud breaches.

```bash
aws --profile target sts get-caller-identity
# Arn: arn:aws:iam::123456789012:user/support/clouddesk-plove
```
Username/path hints (`clouddesk`, `support`) can *suggest* likely privileges (e.g. IAM helpdesk-style permissions to reset credentials) even before confirming anything via the API — useful low-noise reconnaissance.

**Listing policies attached to the compromised identity:**

```bash
# Inline policies directly on the user
aws --profile target iam list-user-policies --user-name clouddesk-plove
# { "PolicyNames": [] }

# Managed policies attached to the user
aws --profile target iam list-attached-user-policies --user-name clouddesk-plove
# {
#   "AttachedPolicies": [
#     { "PolicyName": "deny_challenges_access",
#       "PolicyArn": "arn:aws:iam::123456789012:policy/deny_challenges_access" }
#   ]
# }
```
No error → confirms the identity has `iam:ListAttachedUserPolicies`. IAM has two policy attachment types:
- **Inline policies** — directly embedded in a single identity, not reusable.
- **Managed policies** — standalone, reusable, attachable to multiple identities.

Identities also **inherit policies from Group membership**:

```bash
aws --profile target iam list-groups-for-user --user-name clouddesk-plove
# Groups: [ { "GroupName": "support", "Arn": ".../group/support/support" } ]

aws --profile target iam list-group-policies --group-name support
# { "PolicyNames": [] }

aws --profile target iam list-attached-group-policies --group-name support
# {
#   "AttachedPolicies": [
#     { "PolicyName": "SupportUser",
#       "PolicyArn": "arn:aws:iam::aws:policy/job-function/SupportUser" }
#   ]
# }
```

`SupportUser` here is an **AWS Managed Policy** (identifiable by the `arn:aws:iam::aws:policy/...` ARN prefix, vs. a customer-managed policy which is scoped to the account ID) — specifically a **job-function** policy (`job-function` keyword in the ARN), giving broad read-only access across many services to troubleshoot support issues.

> **Warning** — AWS Managed Policies are convenient but tend to be overly permissive; there's inherent risk in relying on them alone rather than pairing with tighter custom policies.

**Reading a managed policy's document (policies are versioned):**

```bash
# List versions, note the default
aws --profile target iam list-policy-versions --policy-arn "arn:aws:iam::aws:policy/job-function/SupportUser"
# VersionId v8, IsDefaultVersion: true

# Fetch the actual document for that version
aws --profile target iam get-policy-version \
  --policy-arn arn:aws:iam::aws:policy/job-function/SupportUser --version-id v8
```
`SupportUser`'s document grants broad `Get*`/`Describe*`/`List*` (and a few explicit actions like `support:*`) across many services with `"Resource": "*"` — i.e. wide read-only visibility, no write access.

**Discovering allowed IAM subcommands for a given policy shape** (grep AWS CLI's own help for matching verbs):

```bash
aws --profile target iam help | grep -E "list-|get-|generate-"
```
Representative list of IAM read subcommands surfaced this way: `generate-credential-report`, `generate-organizations-access-report`, `generate-service-last-accessed-details`, `get-access-key-last-used`, `get-account-authorization-details`, `get-account-password-policy`, `get-account-summary`, `get-context-keys-for-custom-policy`, `get-context-keys-for-principal-policy`, `get-credential-report`, `get-group`, `get-group-policy`, `get-instance-profile`, `get-login-profile`, `get-open-id-connect-provider`, `get-organizations-access-report`, `get-policy`, `get-policy-version`, `get-role`, `get-role-policy`, `get-saml-provider`, `get-server-certificate`, `get-service-last-accessed-details[-with-entities]`, `get-service-linked-role-deletion-status`, `get-ssh-public-key`, `get-user`, `get-user-policy`, `list-access-keys`, `list-account-aliases`, `list-attached-{group,role,user}-policies`, `list-groups[-for-user]`, `list-instance-profile*`, `list-mfa-devices`, `list-open-id-connect-provider*`, `list-policies`, `list-policies-granting-service-access`, `list-policy-tags`, `list-policy-versions`, `list-role-policies`, `list-role-tags`, `list-roles`, `list-saml-provider*`, `list-server-certificate*`, `list-service-specific-credentials`, `list-signing-certificates`, `list-ssh-public-keys`, `list-user-policies`, `list-user-tags`, `list-users`, `list-virtual-mfa-devices`.

> Even *read-only* IAM access is a "big deal" — IAM controls all identity/authz data for the account.

**Account-wide summary (single low-noise call):**

```bash
aws --profile target iam get-account-summary | tee account-summary.json
```
Notable fields returned: `Groups`, `Roles`, `PolicyVersionsInUse`, `AccountSigningCertificatesPresent`, `AccountAccessKeysPresent`, various quota fields, and critically:
- `MFADevices`: 0, `MFADevicesInUse`: 0 → **no IAM users have MFA configured**.
- `AccountMFAEnabled`: 0 → **root account has no MFA** either.

Both are major security red flags (credential compromise = full account takeover with no second factor).

> Other summary fields worth knowing: **InstanceProfiles** (authorize EC2 instances with IAM permissions), **Providers** (external Identity Providers federated into AWS), **ServerCertificates** (SSL/TLS certs for services requiring encryption).

**Enumerating all IAM identities/policies:**

```bash
aws --profile target iam list-users  | tee users.json
aws --profile target iam list-groups | tee groups.json
aws --profile target iam list-roles  | tee roles.json

# Only customer-managed (--scope Local) policies that are currently attached somewhere
aws --profile target iam list-policies --scope Local --only-attached | tee policies.json
```
Look for suggestive naming: identities/paths containing `admin` merit priority follow-up.

Per-identity inline/managed policy subcommands (tedious to chain manually):
- Inline: `list-user-policies`, `get-user-policy`, `list-group-policies`, `get-group-policy`, `list-role-policies`, `get-role-policy`
- Managed: `list-attached-user-policies`, `list-attached-group-policies`, `list-attached-role-policies` (+ `get-policy-version` to read each document)

**The efficient one-shot alternative — `get-account-authorization-details`:** returns *all* IAM users, groups, roles, and policies **and their relationships** in one call — same information, far fewer logged API calls.

> **Tip** — Running `get-account-authorization-details` requires the identity to have `iam:GetAccountAuthorizationDetails`. It's not literally a wildcard permission, but it is a broad "meta" permission worth watching for when reviewing policies (it exposes the whole IAM graph).

```bash
aws --profile target iam get-account-authorization-details \
  --filter LocalManagedPolicy | tee account-auth-details.json
```
`--filter` accepts any combination of: `User`, `Role`, `Group`, `LocalManagedPolicy`, `AWSManagedPolicy` — restricts which sections come back.

**Circumventing an explicit-deny via a permitted "meta" action:** Directly listing versions of the `deny_challenges_access` policy fails:

```bash
aws --profile target iam list-policy-versions --policy-arn arn:aws:iam::123456789012:policy/deny_challenges_access
# AccessDenied ... with an explicit deny in an identity-based policy
```
But the *same policy document* is embedded in the output of the (permitted) `get-account-authorization-details --filter LocalManagedPolicy` call — because that action isn't itself denied, only the direct `ListPolicyVersions` call is:

```json
{
  "PolicyName": "deny_challenges_access",
  "PolicyVersionList": [
    {
      "Document": {
        "Statement": [
          {
            "Condition": { "StringEquals": { "aws:ResourceTag/challenge": "true" } },
            "Effect": "Deny",
            "Action": "*",
            "Sid": "DenyAllIAMActionsOnChallengedResources"
          }
        ],
        "Version": "2012-10-17"
      },
      "VersionId": "v1",
      "IsDefaultVersion": true
    }
  ]
}
```
This policy denies **all actions on all resources tagged `challenge: true`**.

> **Lesson (both offense and defense):** permitted actions can leak data that a more specific deny was meant to protect (here, reading a policy's content via a broader "list everything" API instead of the specific blocked API). The same class of bypass applies across services — e.g. reading CloudTrail logs to reconstruct information a policy tries to hide elsewhere.

## 25.5 IAM Resources Enumeration

Objectives: Choosing Between a Manual or Automated Enumeration Approach; Enumerating IAM Resources; Processing API Response Data with JMESPath; Running Automated Enumeration with Pacu; Extracting Insights from Enumeration Data.

### 25.5.1 Choosing Between a Manual or Automated Enumeration Approach

- **Manual** — precise control over exactly what's queried/logged; better for stealth-sensitive (red team) engagements; slower/more tedious.
- **Automated tools** — faster, more thorough coverage, but generate significant log volume that may trigger detections. Test tool behavior/impact ahead of a stealth-required engagement.
- No single "best tool" — train on multiple tools to understand their capabilities/limits, and always understand the underlying technology/API so you're not blindly dependent on any one tool.

### 25.5.2 Enumerating IAM Resources

Recap example resource table for a compromised identity:

| Resource Type | Name | ARN |
|---|---|---|
| IAM::User | clouddesk-plove | `arn:aws:iam::123456789012:user/support/clouddesk-plove` |
| IAM::Group | support | `arn:aws:iam::123456789012:group/support/support` |
| IAM::Policy | SupportUser | `arn:aws:iam::aws:policy/job-function/SupportUser` |

> **Warning** — AWS **custom-managed** policies let admins define reusable permission sets across many users/groups/roles. Convenient, but if crafted too broadly they become an account-wide security risk (one bad policy = many over-privileged identities).

`iam get-policy-version` on the policy's ARN shows exactly which actions are granted — grep the raw policy JSON for interesting prefixes:

```bash
aws --profile target iam get-policy-version \
  --policy-arn "arn:aws:iam::aws:policy/job-function/SupportUser" --version-id v8 \
  | grep -E "iam"
# "iam:GenerateServiceLastAccessedDetails",
# "iam:Get*",
# "iam:List*",
```

### 25.5.3 Processing API Response Data with JMESPath

**JMESPath** = a query language for JSON, built into AWS CLI's `--query` flag, used to filter/transform JSON responses client-side.

> **Tip** — `--filter` (server-side) vs `--query` (client-side, JMESPath) are different mechanisms: `--filter` reduces what the AWS API returns; `--query` reshapes/filters the JSON *after* it's already been returned to your client.

```bash
# Base call
aws --profile target iam get-account-authorization-details --filter User

# Project just the UserName field from every array element
aws --profile target iam get-account-authorization-details --filter User \
  --query "UserDetailList[].UserName"

# Select multiple fields from the FIRST object — array form
aws --profile target iam get-account-authorization-details --filter User \
  --query "UserDetailList[0].[UserName,Path,GroupList]"

# Select multiple fields from the FIRST object — named-object form
aws --profile target iam get-account-authorization-details --filter User \
  --query "UserDetailList[0].{Name: UserName,Path: Path,Groups: GroupList}"

# Filter Projections — only usernames containing "admin"
aws --profile target iam get-account-authorization-details --filter User \
  --query "UserDetailList[?contains(UserName, 'admin')].{Name: UserName}"

# Combine Users + Groups whose Path == /admin/ into one custom JSON object
aws --profile target iam get-account-authorization-details --filter User Group \
  --query "{Users: UserDetailList[?Path=='/admin/'].UserName, Groups: GroupDetailList[?Path=='/admin/'].{Name: GroupName}}"
```

JMESPath syntax notes:
- `Array[]` — flattens/selects every element.
- `Array[0]` — selects the first element (`[1]` second, etc.).
- `[?expr]` — **Filter Projection**: keeps only elements matching `expr` (supports functions like `contains(field, 'substr')` and `==` comparisons).
- `{Key: value, Key2: value2}` — builds a custom JSON object from selected fields.
- `&&` — logical AND between filter conditions, e.g. `?contains(UserName,'admin') && contains(Path,'admin')`.

> **Best practice** — save raw AWS CLI output to local files once, then re-query it locally with a standalone JMESPath tool (`jp`) instead of re-hitting the API for every new query — reduces API call count/log noise.

> Azure CLI supports the same `--query`/JMESPath pattern. Google Cloud CLI doesn't implement it natively, but since its output can be JSON, you can pipe to any external JMESPath tool.

Reference docs: **JMESPath Examples** page, **AWS CLI Filter Output** documentation.

### Extracting Insights from Enumeration Data

Analysis needs a clear objective (e.g., "escalate to Administrator access") — undirected data hoarding doesn't produce actionable findings on its own.

Worked example — escalation-path discovery from `get-account-authorization-details` output:

```bash
aws --profile target iam get-account-authorization-details --filter User Group \
  --query "UserDetailList[?UserName=='admin-alice']"
```
Findings: `admin-alice` is in path `/admin/`, member of groups `amethyst_admin` **and** `admin`, no inline/managed policies of her own, and tagged `{"Key": "Project", "Value": "amethyst"}`.

> **Attribute-Based Access Control (ABAC)** — an authorization model where permissions are evaluated against attributes (commonly **tags**) attached to the subject/resource, rather than fixed roles. Common in public cloud IAM.

```bash
aws --profile target iam get-account-authorization-details --filter User Group \
  --query "GroupDetailList[?GroupName=='admin']"
```
The `admin` group has the AWS Managed Policy **`AdministratorAccess`** attached:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        { "Effect": "Allow", "Action": "*", "Resource": "*" }
    ]
}
```
Full wildcard Action + Resource = complete account control. Any user in this group (e.g. `admin-alice`) is an **Effective Admin**.

```bash
aws --profile target iam get-account-authorization-details --filter User Group \
  --query "GroupDetailList[?GroupName=='amethyst_admin']"
```
`admin-alice`'s *other* group, `amethyst_admin`, carries a custom policy with statements including:

```json
{
  "Action": "iam:*",
  "Condition": { "StringEquals": { "aws:ResourceTag/Project": "amethyst" } },
  "Effect": "Allow",
  "Resource": "arn:aws:iam::*:user/*",
  "Sid": "AllowAllIAMActionsInGroupMembers"
}
```
This grants **any** IAM action (including `iam:CreateAccessKey`) against **any** IAM user tagged `Project: amethyst` — and `admin-alice` herself carries that exact tag. So any member of `amethyst_admin` (e.g. a lower-privileged user like `admin-cbarton`) can mint new access keys for `admin-alice` — a direct privilege-escalation path to full Administrator access, purely from a tag left on the wrong user.

**Two escalation paths identified from this analysis:**
1. Directly compromise `admin-alice`'s own credentials/password (social engineering — no MFA is configured account-wide, from the earlier `get-account-summary` finding) or find any other identity holding `iam:*` / `iam:CreateAccessKey` against her.
2. Find/obtain credentials for another member of the `admin` group, or an identity holding `iam:*` / `iam:AddUserToGroup` permissions to add yourself to it.

> Visualizing effective access as a graph (who-can-become-who) makes these multi-hop paths far easier to spot than reading raw JSON policy documents. Referenced tools: **CloudMapper** (visualizes AWS account configuration to surface issues) and **Awspx** (graphs IAM relationships/attack paths specifically).

Lab exercise: the IAM user **`challenge`** is granted `iam:CreateAccessKey`, letting you mint access keys for any other lab user (e.g. `admin-cbarton`) to practically walk this escalation chain.

> Sifting large real-world enumeration datasets for actionable paths is labor-intensive — automated visualization tooling (CloudMapper/Awspx-style) becomes essential at scale.

## 25.6 Wrapping Up

- AWS reconnaissance gathers information about the target's service provider and cloud resources by interacting with **publicly available services** — no authentication required for this first phase.
- The CSP's own API can be abused (Conditions, Principal validation errors, permitted "meta" actions) to extract information that would otherwise require authentication or that a specific deny policy tried to hide.
- Post-compromise, footprint the level of access the stolen credentials grant — sometimes directly queryable (if IAM read access is available), sometimes requiring guesswork/brute force (noisier, less stealthy).
- Enumerate IAM resources (users, groups, roles, policies) manually or with tools (Pacu), then **analyze** — not just collect — that data to identify concrete privilege-escalation paths (tag misconfigurations, overly broad wildcard policies, missing MFA, group-inherited over-permissions).

## Key Takeaways / Workflow Summary

1. **External recon first, no credentials needed:** DNS (`host -t ns`, `whois`, reverse lookups) → identify hosting CSP by nameserver/PTR naming patterns → browser DevTools / `curl | grep -oP` to spot S3-style bucket URLs in page assets → test bucket listability → `cloud_enum` (multi-cloud, keyword/keyfile-driven) to brute-force bucket-name variants across AWS/Azure/GCP.
2. **Abuse the public API before/without authenticating as the target:** search publicly-shared AMIs/EBS/RDS snapshots (`ec2 describe-images/describe-snapshots --filters`) to leak the target Account ID; if none are public, brute-force the Account ID digit-by-digit via S3 bucket **Condition**-scoped IAM policies (`s3:ResourceAccount`); enumerate IAM user/role *existence* in another account by exploiting `Invalid principal in policy` errors on resource policies / trust policies (automatable with **Pacu**'s `iam__enum_roles`/`iam__enum_users`).
3. **Post-compromise footprinting, stealth-aware:** `sts get-caller-identity` (logged, never denied) vs stealthier `iam get-access-key-info` (run from attacker's own account) vs abusing unlogged **data-event** errors (e.g. invoking a nonexistent Lambda) vs querying in a non-default region to dodge default-view CloudTrail monitoring.
4. **Scope IAM permissions methodically:** `list-user-policies` / `list-attached-user-policies` → `list-groups-for-user` → `list-{attached-}group-policies` → `get-policy-version` for each managed policy; or shortcut everything with **one** call: `iam get-account-authorization-details` (optionally `--filter User|Group|Role|LocalManagedPolicy|AWSManagedPolicy`).
5. **Process results with JMESPath (`--query`)** rather than repeated API calls — flatten arrays (`[]`), pick indices (`[0]`), filter projections (`[?contains(...)]`, `&&`), reshape into custom JSON (`{Key: expr}`). Save raw output to files and post-process locally (`jp`) to minimize CloudTrail footprint.
6. **Automate at scale with Pacu** (`import_keys`, `ls`, `help <module>`, `run <module>`, `data <SERVICE>`) — but always understand what a tool is doing under the hood; automated brute-forcing of permissions/roles is noisy and log-heavy, unsuitable for stealth-sensitive engagements without prior impact testing.
7. **Turn raw enumeration into attack paths, not just inventory:** hunt for missing MFA (`get-account-summary`), wildcard Action/Resource policies (`AdministratorAccess`-style), ABAC tag misconfigurations that leak elevated access to lower-privileged group members, and any identity holding `iam:*`, `iam:CreateAccessKey`, or `iam:AddUserToGroup` — these are the concrete mechanisms of privilege escalation once inside.
